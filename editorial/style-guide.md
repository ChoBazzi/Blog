# 한국어 기술 블로그 편집 기준

이 지침은 개인의 실제 경험과 기술적 판단을 독자가 확인할 수 있게 정리하기 위한 것이다. 이력서·자기소개서·검색 광고문을 만들거나 성과를 부풀리는 기준이 아니다. 상위 기준은 루트 `AGENTS.md`이다.

## 문체와 글의 범위

기존 기술 글의 도입·문제 설명에서 `했다`, `이다`, `필요했다` 형태와 환경·구현을 설명하는 문체를 관찰했다. 긴 원문이나 민감한 경험은 예시로 복사하지 않는다. 기술 글에는 간결한 `이다`체를 사용하고 About·연락처처럼 명시적으로 독자 응대용인 글에만 `습니다`체를 쓴다.

한 글은 주요 질문 하나에 답한다. 시작 부분에서 문제 또는 핵심 결론, 독자가 얻을 내용과 적용 범위를 설명한다. 제목·요약은 본문이 입증하는 수준을 넘지 않는다. 글 길이, 실패 횟수, 숫자, 질문형 소제목, 감상이나 철학적 결론을 의무화하지 않는다.

## 설명의 정확성

- 기술 용어와 식별자는 정확하게 쓴다. 필요한 약어·선행 개념은 처음 등장할 때 풀어 설명한다. 쉬운 비유가 실제 동작과 다르면 적용 범위를 밝히거나 쓰지 않는다.
- 주어와 행동을 분명하게 한다. 팀의 결과와 개인이 맡은 일을 분리한다. 개인 학습·로컬 실험·개인 서버 운영·실무 운영을 같은 경험으로 표현하지 않는다.
- 실제 시도·실패·결과만 기록한다. 당시의 선택 이유는 기록이나 작성자 설명이 있어야 한다. 코드만 보고 고민·감정·현장 대사를 만들어내지 않는다.
- 수치가 없으면 만들지 않는다. 미측정 효과는 미측정이라고 밝히고 실제로 검증한 정성적 범위만 서술한다. 숫자에는 환경·단위·기준선·절차·반복 횟수·원자료를 연결한다.
- 가능성·추정·의견은 그 수준을 유지한다. 순서를 인과로 바꾸거나 제한 조건을 지워 단정하지 않는다. 과도한 수식어·자기 칭찬·일률적 감상은 줄인다.
- 참고문헌 목록만 붙이지 않는다. 핵심 주장 가까이에 그 주장을 뒷받침하는 공식 문서의 버전·절 또는 공개 가능한 출처 링크를 둔다. 비공개 장부 경로를 공개 본문에 노출하지 않는다.

## 코드와 검증

코드 앞에는 목적·입력·필요 환경을, 뒤에는 동작·확인 방법·주의점을 설명한다. 아래 세 종류를 혼동하지 않는다.

| 표시 | 의미 | 필요한 설명 |
| --- | --- | --- |
| 구현한 코드 | 실제 저장소에 있는 구현 또는 명시적으로 발췌한 일부 | 파일·버전·생략 범위와 실행 여부 |
| 실행해 확인한 예제 | 해당 환경에서 직접 실행하고 결과를 관찰한 예제 | 실행 주체·명령·버전·결과와 한계 |
| 설명용 의사 코드 | 원리를 설명하기 위한 비실행 코드 | 실행 예제가 아님을 명시 |

예제 실행 전에 스크립트·부작용을 읽는다. 운영 DB·개인정보·프로덕션 자격증명을 사용하지 않는다. 안전하게 격리할 수 없으면 실행하지 않고 미실행과 영향 범위를 적는다. 제공받은 로그를 에이전트 직접 실행으로 바꾸지 않는다.

## 기존 Markdown 형식

현재 사이트는 Next.js에서 `content/`의 Markdown을 읽는다. 기존 필수 frontmatter는 `title`, `description`, `date`, `tags`, `published`이다. `date`는 `YYYY-MM-DD`, `tags`는 인라인 배열, `published`는 boolean이다. `category`·`cover`는 실제 필요한 기존 선택 필드만 사용한다. 새 플랫폼 필드나 외부 스킬의 `author`, `keywords`를 자동 추가하지 않는다.

초안·후보는 `.blog-work/<slug>/`에만 저장하며 `published: false`를 유지한다. 이 플래그만으로 비공개가 보장되지는 않는다. Git 제외와 빌드·배포 제외를 별도로 확인한다. 코드 펜스에 실제 언어 이름을 붙이고, 이미지에는 Markdown 이미지 구문과 의미 있는 대체 텍스트를 사용한다. Obsidian 이미지 임베드 `![[...]]`는 기존 검사가 미지원으로 안내하므로 새 후보에 사용하지 않는다. 기존 글은 자동 변환하지 않는다.

## 독립 작성한 합성 교정 예시

아래 세 사례는 편집 규칙을 보여 주는 **합성 예시**이다. 작성자의 실제 경험·수치·성과로 저장하지 않는다. 추가 맥락은 예시 안에서만 유효하다.

### 미측정 개선 주장

- 주어진 근거: 캐시 분기를 구현했으나 응답 시간을 측정하지 않았다.
- 교정 전: “캐시를 적용해 응답 속도를 획기적으로 개선했다.”
- 교정 후: “캐시를 조회하는 분기를 추가했다. 응답 시간 변화는 측정하지 않았다.”
- 이유: 구현 사실과 성능 효과를 분리한다. `획기적`만 지우고 `개선했다`를 남겨도 근거 없는 주장이므로 기술 검토에서 범위를 먼저 바로잡는다.

### 팀 성과의 개인 성과화

- 주어진 근거: 팀이 배포 절차를 변경했으며 작성자는 설정 검토를 맡았다.
- 교정 전: “배포 절차를 혼자 개선해 팀의 문제를 해결했다.”
- 교정 후: “팀에서 배포 절차를 변경했고, 나는 설정 검토를 맡았다.”
- 이유: 결과와 역할을 구분한다. 새로운 리더십·구현·성과 수치를 추가하지 않는다. 사실 범위를 고치는 일은 근거 검토 후 메인이 반영한다.

### 가능성을 확정으로 바꾸는 교정 방지

- 교정 전: “재시도 간격을 늘리면 요청이 겹칠 가능성을 줄일 수 있을 것으로 보인다.”
- 잘못된 교정: “재시도 간격을 늘려 요청 충돌을 해결했다.”
- 교정 후: “재시도 간격을 늘리면 요청이 겹칠 가능성이 줄어들 것으로 보인다.”
- 이유: 번역투만 줄이고 가설을 유지한다. 적용·실행·해결을 새로 주장하지 않는다. 원문이 이미 명확하다면 유지해도 된다.

## 검토 기준

기술 사실 오류·근거 부족과 문체 취향을 구분한다. 문제가 없는 문장에는 지적을 만들지 않는다. 한국어 교정은 수정본과 변경 이유를 반환하며 논지·목차를 바꾸는 일은 작성 단계로 돌린다. 교정 후 코드·수치·버전·URL뿐 아니라 주장 강도·조건·인과·기여 범위를 재확인한다. 검사 통과는 사실 전체의 보증도 발행 승인도 아니다.
