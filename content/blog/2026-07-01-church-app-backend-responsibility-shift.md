## 배경

상3동성당 앱은 본당 신자들이 주보, 전례력, 매일미사, 공지사항을 쉽게 확인할 수 있도록 만드는 모바일 앱 프로젝트다.

초기 앱은 백엔드가 주보 PDF를 제공하고, 클라이언트 앱이 현재 날짜를 기준으로 어떤 주보를 보여줄지 계산하는 구조에 가까웠다. 전례력과 매일미사도 앱에서 직접 가져오거나 가공하는 흐름이 섞여 있었다. 기능이 주보 조회에 가까울 때는 빠르게 만들 수 있었지만, 운영과 확장을 생각하기 시작하면서 구조의 한계가 보였다.

이번 글은 기술 스택을 바꾼 기록이라기보다, **어떤 책임을 클라이언트에 두고 어떤 책임을 서버에 둘 것인가**를 다시 정리한 기록이다.

## 기존 구조의 문제

초기 구조에서 백엔드는 파일 제공자에 가까웠다. 앱은 현재 날짜를 기준으로 주보를 고르고, 외부 데이터나 날짜 기반 정보를 직접 다뤄야 했다.

이 방식은 빠르게 시작하기에는 편했다. 서버가 단순하니 구현할 것도 적었고, 모바일 화면에서 필요한 값을 바로 계산하면 됐다. 하지만 운영 관점에서는 세 가지 문제가 있었다.

첫째, 외부 데이터 구조가 바뀌면 앱 수정으로 이어질 수 있었다. 전례력, 매일미사, 날짜 기준 콘텐츠 선택 같은 로직이 앱 안에 있으면 작은 정책 변경도 모바일 앱 재배포 부담으로 연결된다.

둘째, 기능 확장이 어려웠다. 공지사항, 푸시 알림, 게시판 같은 기능은 서버가 데이터와 상태를 안정적으로 관리해야 한다. 하지만 PDF 조회 중심 구조에서는 게시 상태, 노출 기간, 관리자 권한 같은 개념을 자연스럽게 확장하기 어렵다.

셋째, 앱의 책임이 너무 무거웠다. 모바일 앱은 화면 표시와 사용자 경험에 집중해야 하는데, 실제로는 날짜 계산, 데이터 파싱, 외부 의존 처리까지 담당하고 있었다.

## 고민한 지점

처음에는 클라이언트에서 처리하는 방식이 더 빠르게 느껴졌다. 앱에서 날짜를 계산하고 필요한 데이터를 바로 보여주면 서버 API를 많이 만들지 않아도 된다.

하지만 성당 앱은 한 번 만들고 끝나는 화면이 아니라 매주 주보가 바뀌고, 전례력과 미사 정보가 계속 갱신되는 서비스다. 이 경우 중요한 것은 첫 구현 속도보다 **운영 중 변경을 어디에서 흡수할 수 있는가**였다.

그래서 책임을 다음 기준으로 나눴다.

- 운영자가 바꾸는 데이터는 서버가 소유한다.
- 날짜 기준으로 어떤 콘텐츠를 보여줄지 결정하는 로직은 서버가 담당한다.
- 외부 데이터를 수집하고 정규화하는 일은 서버가 맡는다.
- 앱은 서버가 내려준 상태를 사용자에게 읽기 쉽게 보여준다.

이 기준으로 보면 주보 현재 날짜 계산, 전례력 데이터, 매일미사 수집, 공지 게시 상태는 클라이언트보다 서버에 두는 편이 더 자연스럽다.

## 개선 방향

백엔드는 Spring Boot 기반으로 다시 구성했다. 핵심 목표는 클라이언트에 있던 도메인 로직을 서버로 옮기는 것이었다.

```text
React Native App
  -> Spring Boot API
  -> PostgreSQL
  -> File Storage
```

개선 방향은 다음과 같다.

- 주보의 현재 날짜 계산은 서버가 담당한다.
- 주보 PDF와 이미지 파일은 서버에서 관리한다.
- 전례력 데이터는 서버 DB에서 검수와 게시 상태를 관리한다.
- 매일미사 데이터는 서버가 수집하고 정규화한다.
- 앱은 API를 조회하고 화면에 표시하는 역할에 집중한다.

이 구조로 바꾸면 외부 데이터나 운영 정책이 바뀌어도 서버 수정으로 대응할 수 있다. 모바일 앱 재배포 부담도 줄어든다.

## 현재 백엔드 구조

Spring Boot 백엔드는 도메인별로 기능을 나누는 방향으로 잡았다.

- `bulletin`: 본당 주보, 교구 주보, PDF 업로드, 이미지 변환
- `liturgy`: 전례력 데이터 조회
- `mass`: 매일미사 수집 및 조회
- `notice`: 공지사항
- `prayer`: 기도문
- `schedule`: 미사 시간표
- `church`: 본당 정보

API는 모바일 앱이 사용하기 쉬운 REST 형태로 구성했다. 예를 들어 앱은 현재 주보를 직접 계산하지 않고 현재 주보 API를 호출한다.

```text
GET /api/v1/bulletins/current
```

전례력도 앱에 전체 데이터를 하드코딩하지 않고 기간 기준으로 조회한다.

```text
GET /api/v1/liturgical-days?from=2026-05-01&to=2026-05-31
```

이 구조에서는 서버가 “현재 보여줄 데이터”를 결정하고, 앱은 “어떻게 보여줄지”에 집중한다.

## 프론트엔드 책임 정리

모바일 앱은 Expo와 React Native 기반으로 다시 구성했다. 주요 탭은 홈, 주보, 전례력, 미사, 더보기로 나눴다.

앱의 역할은 서버에서 받은 데이터를 사용자가 읽기 쉽게 보여주는 것이다. 특히 성당 앱은 고령층 사용자도 고려해야 하므로 큰 글씨, 단순한 흐름, 명확한 메뉴 구조가 중요하다.

서버 중심 구조로 바꾼다고 해서 앱이 단순해지는 것만은 아니다. 앱은 대신 다음 책임에 더 집중해야 한다.

- 서버 응답을 화면 흐름에 맞게 배치하기
- 로딩, 빈 상태, 오류 상태를 명확하게 보여주기
- 네트워크 실패 상황에서도 사용자가 다음 행동을 알 수 있게 하기
- 사용자가 자주 확인하는 정보를 홈에서 빠르게 보여주기

즉 앱의 책임을 줄인 것이 아니라, 앱이 잘해야 하는 책임만 남긴 것이다.

## 배운 점

이번 전환을 통해 가장 크게 배운 점은 클라이언트와 서버의 책임을 구현 편의가 아니라 운영 기준으로 나눠야 한다는 점이다.

처음에는 앱에서 처리하는 것이 빠르게 느껴졌다. 하지만 운영 단계에서는 서버가 소유해야 하는 책임이 분명히 있었다.

특히 다음 로직은 서버에 두는 편이 더 적합했다.

- 날짜 기준 콘텐츠 선택
- 외부 데이터 수집
- 게시와 비공개 상태 관리
- 관리자 기능
- 알림 발송 기준
- 파일 저장과 공개 URL 관리

반대로 클라이언트는 화면 표시, 사용자 설정, 캐시, 접근성에 집중하는 편이 유지보수하기 좋았다.

## 앞으로의 계획

앞으로는 관리자 기능을 더 강화할 예정이다. 우선 공지사항 작성과 주보 업로드 기능을 안정화하고, 이후 푸시 알림과 게시판 기능을 추가할 계획이다.

게시판은 사용자 작성 콘텐츠가 들어가기 때문에 단순 CRUD로 끝나지 않는다. 권한, 신고, 숨김 처리, 관리자 검수 같은 정책을 함께 설계해야 한다. 이 부분도 클라이언트가 직접 처리할 수 있는 영역이 아니라 서버가 정책을 소유해야 하는 영역이다.

최종 목표는 단순히 PDF를 보여주는 앱이 아니라, 본당 소식과 신앙 생활 정보를 안정적으로 제공하는 본당 생활 플랫폼으로 발전시키는 것이다.

## 정리

이번 구조 개선은 단순한 기술 스택 변경이 아니었다. 앱의 책임 구조를 다시 설계한 경험이었다.

기존에는 클라이언트가 많은 로직을 직접 처리했지만, Spring Boot 백엔드로 전환하면서 데이터 소유권과 운영 책임을 서버로 옮겼다. 이를 통해 앱 재배포 부담을 줄이고, 공지사항, 알림, 게시판 같은 기능을 추가할 수 있는 기반을 만들었다.

신입 개발자로서 이 프로젝트를 통해 API 설계, 서버와 클라이언트의 책임 분리, 운영을 고려한 백엔드 구조의 중요성을 배웠다. 앞으로는 기능을 빨리 붙이는 것뿐 아니라, 그 기능이 운영 중 어디에서 변경되고 누가 책임지는지를 먼저 생각하려고 한다.
