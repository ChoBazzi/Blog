## 문제와 평가 범위

BizKit에는 명함 배경 생성, 자기소개와 GitHub 활동 분석, 임베딩 검색처럼 서로 다른 모델이 필요했다. 나는 이미지 생성·LLM·임베딩 모델을 비교했다. VLM OCR 모델 비교는 내 담당이 아니었다.

모델을 고를 때는 서비스에서 맡길 역할을 먼저 나눴다. 명함의 글자는 별도 렌더러로 배치하고, 점수 계산은 정형화할 수 있는 지표에 한정했다. 다만 이 구분이 처음부터 완성돼 있었던 것은 아니다. GitHub 활동을 6각 차트로 보여주는 HEX에서는 LLM의 점수 보정도 계획했다. 근거 부족을 인정하고 방향을 바꾼 과정은 [개발 회고](/projects/2026-05-28-bizkit-ai-retrospective-draft)에 정리했다.

아래 수치는 당시 위키에 남긴 비교 기록이며, 새로 실행한 실험 결과는 아니다. 일부 평가 조건이 빠져 있어 모델의 일반적인 우열이나 운영 성능까지 판단하기에는 부족하다.

| 영역 | 기록된 환경 | 입력 규모 | 결과를 읽는 범위 |
|---|---|---|---|
| 이미지 생성 | Colab A100 중심, Qwen-Image는 H100, Gemini는 외부 API | 프롬프트 3종 | 서로 다른 실행 조건에서의 배경 생성 비교 |
| LLM | RunPod Serverless L40 | HEX 10개·Job 10개 | 평가 리포트의 입력 규모. 성능 측정 반복·유효 요청 분모와 동일하다고 단정하지 않음 |
| 임베딩 | 오프라인 비교와 Milvus 통합 | corpus 100개, 과제별 평가셋 | 작은 평가셋의 보고값. 운영 데이터 전체를 대표하지 않음 |

## 이미지 생성 모델 비교

명함에서는 이름이나 연락처를 모델이 잘못 그리면 결과물을 사용할 수 없다. 그래서 배경 생성과 텍스트 렌더링을 분리하고, 배경 모델에서는 글자를 올릴 여백과 질감·조명이 적절한지 살폈다.

[이미지 생성 모델 위키](https://github.com/100-hours-a-week/18-team-18TEAM-wiki/wiki/이미지생성모델)의 요약 표에는 다음 값이 기록돼 있다. 배경 안정성은 당시의 주관 평가이며, 블라인드 평가나 사용자 선호도 조사 결과는 아니다.

| 후보 | 기록된 추론 시간 범위 | 기록된 Peak VRAM | 배경 안정성 평가 |
|---|---|---|---|
| SDXL Base | 2.86~2.88s | 9.21GB | 높음 |
| SD3.5 Large Turbo | 9.20~12.74s | 6.09GB | 중 |
| Z-Image Turbo | 2.80~4.70s | 20.85GB | 중~높음 |
| Korean SD v1.5 | 1.76~3.85s | 4.15GB | 낮음 |
| Qwen-Image | 8.59~10.36s | 59.71GB | 높음 |
| Gemini 3 Pro Image 계열 | 12.45~16.76s | 클라우드 API로 비교 불가 | 높음 |

SDXL Base를 선택했다. 이 모델의 개별 결과 표에는 해상도 `1104×624`, 25 steps, guidance scale 7.5와 다음 값이 남아 있다.

| 프롬프트 | 시드 | 추론 시간 | Peak VRAM |
|---|---|---|---|
| p1 | 101 | 2.88s | 9.21GB |
| p2 | 102 | 2.86s | 9.21GB |
| p3 | 103 | 2.86s | 9.21GB |

공통 프롬프트는 위키에 남아 있지만 GPU·해상도·steps가 모든 후보에서 같지는 않다. 프롬프트별 독립 반복 횟수, 워밍업과 메모리 측정 범위도 충분히 남아 있지 않아 모델 고유의 속도 순위나 실제 운영 단가를 계산하기 어렵다. 같은 위키의 설명 문단과 개별 결과 표에도 수치 차이가 있어, 위 값은 개별 결과 표를 기준으로 옮겼다.

배경 생성과 연락처 렌더링을 나눈 것은 출력 제어를 위한 선택이었다. 이 글에 제시한 자료만으로는 GPU 운영과 외부 API의 비용을 비교해 절감률이나 손익분기점을 판단하기 어렵다.

## LLM 평가 기록

[LLM 리포트](https://github.com/100-hours-a-week/18-team-18TEAM-wiki/wiki/LLM)는 2026-02-03 생성된 기록이다. HEX와 자기소개 생성인 Job을 각각 10개 입력으로 평가하고, 웜업 후 요청 지연과 cold start를 별도로 기록했다.

### 응답 시간과 생성 속도

| 모델 | Cold Start | 평균 Latency | Tokens/sec |
|---|---|---|---|
| Qwen2.5 7B Instruct | 33149ms | 15386ms | 36.8 |
| EXAONE 3.5 7.8B Instruct | 39944ms | 15121ms | 31.4 |
| Llama 3.1 8B Instruct | 39041ms | 18034ms | 26.6 |
| Qwen3 8B | 90573ms | 25793ms | 24.5 |

`Tokens/sec`는 토큰 생성 속도 지표이며 API가 초당 처리한 요청 수와 같지 않다. 리포트에는 성공률 100.0%, JSON 파싱 실패율 0.00%도 있지만, 재시도 전후 중 어느 시점의 결과인지와 실패를 포함한 요청 분모는 확인하지 못했다. 운영 중 실패가 없었다는 뜻으로 읽을 수는 없다.

P95와 P99는 모델별로 동일하게 기록돼 있다. 백분위 계산 방식과 실제 성능 표본 수를 확인하지 못해 비교 표에서는 제외했다. 작은 입력셋에서 얻은 값으로 운영 지연을 보장하기도 어렵다.

### 품질 점수의 한계

리포트에는 다음 가중치가 명시돼 있다.

| 항목 | HEX 가중치 | Job 가중치 |
|---|---|---|
| JSON 스키마 준수 | 25% | 20% |
| 점수·내용 정확도 | 25% | 25% |
| 한국어 품질 | 20% | 25% |
| 일관성·검색 컨텍스트 | 15% | 15% |
| 환각 탐지 | 15% | 15% |

그러나 평가자, 세부 채점 규칙, 환각 지표의 점수 방향, 종합 점수의 성능 정규화 방식은 확인하지 못했다. 특히 공개된 EXAONE HEX 세부 평균에 각 가중치를 곱해 합산하면 `0.96640`인데, 리포트의 가중 평균은 `0.870`이다. 원시 평가 결과 없이는 차이가 생긴 이유와 어느 값이 맞는지 판단할 수 없다.

리포트는 Qwen2.5 7B Instruct를 최종 권장했다. 다만 HEX·Job 가중 평균과 종합 점수의 계산을 확인할 수 없어, 모든 품질 항목에서 우수했는지나 모델 간 점수 차이가 재현되는지는 별도 검증이 필요하다.

또한 HEX 점수의 참조값 대비 편차를 평가하는 것은 개발자의 실제 협업 역량을 측정하는 것과 다르다. 모델이 정해진 출력 규칙을 따르는지와 점수 체계 자체의 타당성을 구분해야 한다.

## 임베딩 평가 기록

[임베딩 위키](https://github.com/100-hours-a-week/18-team-18TEAM-wiki/wiki/임베딩모델)는 2026-02-11의 오프라인 비교와 Milvus 통합 결과를 담고 있다.

| 평가셋 | 기록된 규모 |
|---|---|
| 검색 대상 corpus | 100개 |
| IT 직무 검색 | 38개 질의 |
| 시맨틱 캐싱 | 18개 쌍 |
| 자연어 검색 | 16개 질의 |
| IT 분류 | 136개 입력 |

Recall@5는 일반적으로 정답 항목이 상위 5개 검색 결과에 얼마나 포함되는지를 나타낸다. 정답이 질의마다 하나인 평가에서는 상위 5개 안에 정답이 들어간 질의 비율과 같다. MRR은 첫 정답 순위의 역수를 평균한 값이다. F1은 분류의 precision과 recall을 함께 보는 지표이며, 단순 정확도와 같지 않다.

원문에는 질의별 정답 수와 누락·제외된 질의의 처리 방식이 충분히 남아 있지 않다. 실제 집계에 포함된 질의 수가 명시된 평가셋 크기와 같은지도 확인이 필요하다.

### 오프라인 비교의 보고값

| 모델 | Recall@5 | MRR | 자연어 검색 MRR | 분류 F1 |
|---|---|---|---|---|
| BGE-m3-ko | 1.0000 | 0.9551 | 0.9062 | 0.9846 |
| BGE-m3 | 1.0000 | 0.9551 | 0.8750 | 0.9846 |
| KURE-v1 | 1.0000 | 0.9359 | 0.8771 | 0.9846 |
| gte-base-korean | 1.0000 | 0.9295 | 0.8792 | 0.9846 |
| Qwen3-0.6b | 1.0000 | 0.8590 | 0.7479 | 0.9846 |
| KoELECTRA | 0.4615 | 0.3449 | 0.1888 | 0.3810 |

당시에는 BGE-m3-ko를 선택했다. 위 MRR 차이는 해당 평가셋의 보고값으로, 모든 검색에서 첫 번째 결과가 더 정확하다는 의미는 아니다.

모델 크기를 MB로 적은 원문 표는 파일 용량인지 메모리 사용량인지, 어떤 dtype으로 비교했는지가 불분명하다. 이 값으로 BGE-m3-ko가 BGE-m3보다 절반 크기라고 판단하기는 어렵다. 분류 임계값 `0.81`도 이 실험에서 선택한 값이다. 서비스 전체에 적용할 보편적인 기준은 아니며, 임계값 조정용 데이터와 최종 평가 데이터가 독립적인지도 확인하지 못했다.

### Milvus 통합의 보고값

| 구성 | Recall@5 | MRR | 단일 쿼리 | 배치 쿼리 | E2E latency |
|---|---|---|---|---|---|
| BGE-m3-ko + IVF_FLAT | 1.0000 | 0.9551 | 1.7ms | 8.0ms | 147.5ms |
| BGE-m3-ko + HNSW | 1.0000 | 0.9551 | 2.0ms | 11.8ms | 153.3ms |
| KURE-v1 + IVF_FLAT | 1.0000 | 0.9359 | 2.9ms | 11.4ms | 164.4ms |
| KURE-v1 + HNSW | 1.0000 | 0.9359 | 2.5ms | 12.5ms | 171.5ms |

보고서의 corpus는 100개이다. 인덱스 파라미터, 하드웨어, 반복 횟수, 분산, 배치 크기와 E2E 측정 구간을 충분히 확인하지 못해, `1.7ms`와 `2.0ms`의 차이만으로 IVF_FLAT이 일반적으로 더 빠르다고 판단하기는 어렵다.

이 표는 당시 비교 조건이다. 현재 확인한 임베딩 서비스 코드는 컬렉션 생성에 `AUTOINDEX`를 사용한다. 실험에서 IVF_FLAT을 선택했다는 기록만으로 전체 운영 기간의 설정까지 알 수는 없다.

## 선택과 배포의 구분

기록상 이미지 배경 생성은 SDXL Base, LLM 리포트의 권장 모델은 Qwen2.5 7B Instruct, 임베딩 비교의 선택은 BGE-m3-ko와 IVF_FLAT이었다. 다만 후속 README에는 Qwen3-8B-AWQ가 있고, 임베딩 코드의 기본 인덱스도 실험과 다르다.

비교 당시의 선택과 후속 설정은 구분해야 한다. 남은 기록만으로 전체 운영 기간의 모델·인덱스 변경 이력을 확정할 수 없고, 후속 평가는 과거 선택 당시의 측정과도 별개이다.

## 결과와 배운 점

기능별로 모델을 비교하고 텍스트 렌더링, 정형 점수 계산, 벡터 검색처럼 모델 밖에서 책임질 부분을 나눴다. 하지만 지표를 표로 남기는 것만으로 비교가 재현 가능해지지는 않았다.

앞으로는 입력과 정답, 평가 코드·설정, 실행 환경, 실패·재시도를 포함한 요청별 결과를 함께 남겨야 한다. 그래야 표의 차이가 모델 때문인지 실험 조건 때문인지 다시 확인할 수 있다.
