## 요약

BizKit은 팀 CARO가 개발한 서비스로, 개발자의 이력과 활동 데이터를 바탕으로 명함 생성, 명함 OCR, 직무 기반 자기소개 생성, GitHub 기반 6각 차트 분석, 자연어 검색을 제공하는 카카오테크 부트캠프 파이널 프로젝트입니다.

저는 이 프로젝트에서 AI 서버 영역을 맡았습니다. 단순히 모델 API를 호출하는 서버가 아니라, 긴 작업을 비동기로 처리하고, LLM과 이미지 모델의 출력을 서비스가 사용할 수 있는 데이터로 제한하는 구조를 설계했습니다.

- 구분: 카카오테크 부트캠프 파이널 팀 프로젝트
- 역할: AI 서버 설계 및 구현, API 명세 작성, 모델 벤치마크, 기능별 파이프라인 설계
- 주요 기술: FastAPI, Redis Streams, RunPod Serverless, vLLM, SDXL, Milvus, BGE-m3-ko
- 링크: [AI Repo](https://github.com/100-hours-a-week/18-team-18TEAM-ai), [AI Wiki](https://github.com/100-hours-a-week/18-team-18TEAM-wiki/wiki/AI-Wiki)

이 글은 프로젝트 전체 맥락을 빠르게 파악할 수 있도록 정리한 메인 글입니다. 상세 설계와 모델 선택 과정은 별도 글로 분리했습니다.

## 문제

AI 기능은 일반적인 CRUD API와 다르게 동작합니다. 명함 생성은 Diffusion 모델과 텍스트 렌더링이 필요하고, 직무 분석과 6각 차트 분석은 LLM 호출과 외부 API 호출이 필요합니다. 자연어 검색은 임베딩 모델과 Vector DB가 함께 움직여야 합니다.

처음부터 중요했던 문제는 세 가지였습니다.

| 문제 | 왜 중요한가 | 설계 방향 |
|---|---|---|
| 긴 응답 시간 | LLM, OCR, Diffusion은 요청 시간이 길고 cold start가 발생할 수 있음 | 요청 접수와 실행을 분리 |
| 출력 불안정성 | LLM은 JSON을 깨거나 근거 없는 점수를 만들 수 있음 | 스키마 검증, 규칙 기반 계산, 후처리 적용 |
| 모델별 자원 차이 | Diffusion, LLM, Embedding은 GPU/latency/비용 특성이 다름 | FastAPI와 모델 서빙 경로를 분리 |

이 문제를 해결하지 않으면 AI 기능은 데모에서는 동작해도 서비스 안에서는 쉽게 흔들립니다. 그래서 목표는 "좋은 모델을 붙이기"가 아니라, 모델 호출을 실패 상태와 API 계약을 가진 백엔드 기능으로 만드는 것이었습니다.

## 전체 구조

Spring Backend는 사용자, 명함, 리뷰, 권한 같은 도메인 계약을 담당하고, FastAPI AI 서버는 모델 호출과 후처리 흐름을 담당하도록 나눴습니다.

```text
Frontend
  -> Spring Backend
  -> FastAPI AI Orchestrator
  -> Redis Streams
  -> AI Worker
  -> RunPod Model Serving
  -> Result Store
```

대부분의 AI API는 `task_id` 기반 비동기 작업으로 설계했습니다. 클라이언트는 작업을 요청한 뒤 상태와 결과를 조회합니다.

```text
pending
  -> running
  -> completed
  -> failed
```

이 구조는 구현량이 늘어나지만, 긴 작업과 실패를 서비스 흐름 안에서 다루기 쉬워집니다. API 서버는 작업 접수에 집중하고, Worker는 기능별 파이프라인과 모델 호출을 처리합니다.

## 주요 기능

### 명함 생성

명함 생성은 사용자의 명함 정보와 스타일 요청을 받아 배경 이미지를 만들고 텍스트를 오버레이하는 기능입니다.

처음에는 이미지 생성 모델이 명함 전체를 한 번에 만들어주는 방식도 고려할 수 있었습니다. 하지만 명함에서는 이름, 전화번호, 이메일, 주소가 한 글자라도 틀리면 결과물을 사용할 수 없습니다. 그래서 이미지 모델은 배경만 만들고, 텍스트는 별도 렌더러가 확정하도록 나눴습니다.

```text
style request
  -> LLM prompt/layout hint
  -> SDXL background generation
  -> text renderer
  -> final card image
```

### 명함 OCR

명함 OCR은 사용자가 업로드한 명함 이미지에서 이름, 회사, 직책, 전화번호, 이메일 같은 필드를 추출하는 기능입니다.

이 기능은 인증/인가나 도메인 데이터 조회가 필요하지 않은 독립 작업이라고 판단했습니다. 그래서 Spring을 단순 프록시로 거치지 않고 Frontend가 FastAPI OCR API를 직접 호출하는 흐름으로 설계했습니다.

OCR 결과는 원문 텍스트 그대로 반환하지 않고, 전화번호와 이메일처럼 형식이 명확한 값은 정규화하고, 확신이 낮은 필드는 `confidence`와 함께 내려주도록 제한했습니다.

### 직무 분석

직무 분석은 회사, 부서, 직무, 프로젝트 정보를 바탕으로 자기소개 문단과 검색 신뢰도를 반환하는 기능입니다.

개발과 무관한 직무가 들어오면 LLM이 억지로 개발자 자기소개를 만들면 안 됩니다. 그래서 임베딩 기반 직무 필터를 먼저 거치고, 필요한 경우 검색 API로 회사와 부서 컨텍스트를 보강했습니다.

```text
input validation
  -> embedding job filter
  -> web search context
  -> LLM generation
  -> JSON validation
```

### GitHub 기반 HEX 분석

HEX 분석은 GitHub 활동과 동료 리뷰를 바탕으로 협업, 소통, 기술, 문서화, 신뢰성, 재협업 선호도 6개 축을 계산하는 기능입니다.

여기서 핵심은 점수를 LLM이 만들지 않게 한 점입니다. PR 생성 수, PR 리뷰 수, 이슈 코멘트, 언어 다양성, README 작성 비율, 머지율 같은 관측 가능한 데이터로 점수를 먼저 계산하고, LLM은 그 점수의 의미를 설명하는 역할만 맡겼습니다.

이렇게 해야 같은 입력에 대해 점수가 재현 가능하고, LLM이 근거 없이 결과를 꾸며내는 위험을 줄일 수 있습니다.

## 모델 선택

최종 조합은 기능별 실패 조건을 기준으로 골랐습니다.

| 기능 | 선택 | 선택 이유 |
|---|---|---|
| 명함 배경 생성 | SDXL Base | 2.86s~2.88s, 9.21GB VRAM으로 배경 생성 품질과 운영 비용의 균형이 좋음 |
| LLM 분석 | Qwen2.5 7B Instruct | HEX 0.98, Job 0.86, 36.8 tokens/sec, JSON 실패율 0.00% |
| 임베딩 검색 | BGE-m3-ko | Recall@5 1.0000, MRR 0.9551, Milvus E2E 147.5ms |
| Vector DB 인덱스 | Milvus IVF_FLAT | 프로젝트 규모에서 검색 품질과 운영 단순성의 균형이 좋음 |

모델 선택에서 가장 중요한 기준은 벤치마크 최고점이 아니었습니다. 명함 텍스트 정확도, JSON 안정성, 직무 검색 품질, RunPod 운영 비용처럼 서비스에서 실패하면 안 되는 조건을 먼저 정하고 후보를 좁혔습니다.

자세한 측정 수치는 [BizKit AI 모델 선택과 벤치마크](/projects/2026-05-29-bizkit-ai-model-benchmark)에 따로 정리했습니다.

## 설계에서 중요했던 판단

### 1. Spring 안에 AI 기능을 넣지 않기

AI 모델과 프롬프트는 자주 바뀝니다. 이 변경이 Spring 도메인 서버 배포와 묶이면 팀 전체 배포 리스크가 커집니다. 그래서 Spring은 도메인 정책과 데이터 무결성을 유지하고, FastAPI는 AI 워크플로우와 모델 호출을 담당하도록 경계를 나눴습니다.

### 2. 동기 응답보다 작업 상태를 먼저 설계하기

LLM, OCR, Diffusion은 언제든 늦어질 수 있습니다. 그래서 성공 응답만 설계하는 대신 `pending`, `running`, `completed`, `failed` 상태와 결과 조회 API를 먼저 정의했습니다. AI 기능을 백엔드 기능으로 다루려면 실패 상태가 반드시 필요했습니다.

### 3. 모델 출력보다 서비스 계약을 우선하기

LLM의 자연어 응답은 그럴듯해 보여도 서비스 데이터로 바로 쓰기 어렵습니다. 그래서 JSON 스키마 검증, 점수 계산 분리, 검색 신뢰도 계산, OCR 필드 정규화처럼 모델 앞뒤의 제어 로직을 더 중요하게 봤습니다.

## 결과

이 구조를 통해 AI 기능을 하나의 요청-응답 코드가 아니라, 상태와 실패를 가진 작업 단위로 다룰 수 있었습니다.

- 명함 생성은 배경 생성과 텍스트 렌더링을 분리해 텍스트 오탈자 리스크를 줄임
- 직무 분석은 임베딩 필터와 검색 컨텍스트를 붙여 LLM 호출 품질을 보강
- HEX 분석은 규칙 기반 점수 계산과 LLM 해석을 분리해 재현성을 확보
- 임베딩 검색은 Milvus 통합 후에도 Recall@5 1.0000, MRR 0.9551을 유지

무엇보다 이 프로젝트를 통해 AI 서버도 일반 백엔드처럼 책임 경계, API 계약, 실패 상태, 배포 단위, 관측 가능성을 먼저 설계해야 한다는 기준을 얻었습니다.
