## 문제와 담당 범위

BizKit의 직무 필터와 시맨틱 캐시에는 텍스트를 벡터로 바꾸고 비슷한 항목을 검색하는 기능이 필요했다. 메인 AI 서버가 LLM 호출과 GitHub 데이터 수집뿐 아니라 임베딩 모델 로딩과 Milvus 연결까지 맡으면 관리할 책임이 커졌다.

나는 임베딩 API와 벡터 검색 서비스를 구현하고 메인 AI 서버에서 HTTP로 호출하도록 분리했다. 이 글은 [임베딩 서비스 저장소](https://github.com/100-hours-a-week/18-team-18TEAM-ai2)의 구현과 사용 조건을 설명한다. 모델 비교 수치는 [별도 벤치마크 글](/projects/2026-05-29-bizkit-ai-model-benchmark)에 나눴다.

## 모델 로딩과 API

앱 시작 시 `dragonkue/BGE-m3-ko`와 Milvus 클라이언트를 초기화한다. 모델은 클래스 싱글톤으로 관리하므로 같은 프로세스의 요청마다 다시 로드하지 않는다. 여러 서버 프로세스 전체가 하나의 모델 인스턴스를 공유한다는 의미는 아니다.

`SentenceTransformer`의 인코딩에서 `normalize_embeddings=True`를 사용한다. 이 서비스의 기본 임베딩 차원은 1024이다.

```text
AI 서버 -> 임베딩 서비스 -> BGE-m3-ko -> 벡터
                  |
                  +-> Milvus에 저장·검색
```

| API | 역할 |
|---|---|
| `POST /embed` | 단일 텍스트를 벡터로 변환 |
| `POST /embed/batch` | 여러 텍스트를 배치로 변환 |
| `POST /collection/{name}/insert` | 텍스트를 임베딩하거나 입력 벡터를 사용해 저장 |
| `POST /collection/{name}/search` | 질의를 서비스 모델로 임베딩한 뒤 검색 |
| `POST /collection/{name}/search/vector` | 이미 생성된 질의 벡터로 검색 |

배치 경로는 시드 데이터처럼 여러 문장을 한 번에 처리하기 위한 인터페이스이다. 별도 측정 없이 단일 요청보다 몇 배 빠르다고 표현하지 않는다.

## 컬렉션 처리

컬렉션은 자동 생성 ID와 `text`, `category`, `metadata`, `embedding` 필드로 구성했다. 기본 벡터는 1024차원 `FLOAT_VECTOR`이며, 검색 metric은 `COSINE`이다.

삽입 시 컬렉션이 없으면 생성한다. 반면 없는 컬렉션을 검색하면 404로 반환한다. 데이터를 처음 넣는 상황과 검색할 저장소가 없는 상황을 구분한 것이다. 자동 생성이 잘못 지정한 컬렉션 이름까지 찾아준다는 뜻은 아니므로 호출자는 이름을 일관되게 관리해야 한다.

현재 확인한 코드의 인덱스 생성 설정은 `AUTOINDEX`이다. 모델 비교 실험에서 IVF_FLAT과 HNSW를 평가한 기록이 있지만, 그것을 현재 서비스의 실제 인덱스 설정과 동일하게 설명하지 않는다.

## 벡터 호환 조건

벡터를 직접 받는 API는 같은 벡터를 다시 계산하지 않고 검색에 사용할 수 있는 경로이다. 그러나 외부에서 생성한 벡터를 저장된 데이터와 무조건 비교할 수 있는 것은 아니다.

예를 들어 둘 다 1024차원이어도 서로 다른 모델이 만든 벡터는 좌표가 의미하는 바가 다를 수 있다. 저장된 문서와 질의는 같은 모델과 호환되는 전처리·정규화 조건을 사용해야 한다. API가 배열을 받아들인다는 것과 검색 결과가 의미 있다는 것은 별개이다.

따라서 “다른 모델로 바꾸더라도 API 계약만 유지하면 된다”는 설명은 부족하다. 모델을 교체하면 기존 문서도 새 모델로 다시 임베딩하고, 인덱스와 유사도 임계값을 새 조건에서 확인해야 한다. 서로 다른 공간의 벡터를 같은 컬렉션에 섞지 않는 것이 사용 조건이다.

이 조건은 구현을 설명하며 정리한 주의사항이지, 현재 API가 벡터의 생성 모델과 버전을 자동 검증하거나 모델 마이그레이션을 자동 수행한다는 뜻은 아니다.

## 검색과 서비스 정책의 경계

임베딩 서비스는 가까운 항목과 유사도를 반환한다. 그 결과로 요청을 차단할지, 이전 응답을 재사용할지는 메인 AI 서버의 정책이다.

비슷한 직무 표현을 찾는 것과 완성된 자기소개를 다른 요청에 재사용하는 것은 다른 판단이다. 직무가 비슷해도 이름이나 프로젝트 내용이 다르면 같은 답변을 반환해서는 안 된다. 시맨틱 캐시는 유사도뿐 아니라 사용자별 정보와 결과에 영향을 주는 입력을 함께 고려해야 한다.

직무 필터 역시 검색 지표가 높다는 사실만으로 차단 정책이 정확하다고 볼 수 없다. 통과 대상의 오차단과 차단 대상의 잘못된 통과를 따로 확인해야 한다.

## 검증과 한계

현재 소스에서 모델 초기화, 정규화, 컬렉션 삽입·검색, 없는 컬렉션의 404 처리를 확인할 수 있다. 이 글을 정리하면서 별도 GPU 추론이나 운영 부하 테스트를 재실행하지는 않았다.

당시 모델 비교는 작은 corpus와 과제별 평가셋에서 수행한 기록이다. 모델 검색 지표를 서비스 전체의 필터 정확도나 캐시 안전성, GPU 비용 절감률로 바꾸어 쓰지 않는다. 인덱스 비교와 현재 구현 설정도 구분한다.

## 배운 점

임베딩 서비스를 분리한 결과 메인 AI 서버는 모델 로딩과 Milvus 연결을 직접 관리하지 않아도 됐다. 대신 HTTP 형식뿐 아니라 벡터 공간, 컬렉션, 검색 결과의 사용 정책까지 계약으로 다뤄야 했다.

모델을 바꿀 수 있는 인터페이스를 만드는 것과 기존 데이터를 그대로 사용할 수 있는 것은 다르다. 이 경계를 분명히 하는 것이 서비스 분리만큼 중요했다.
